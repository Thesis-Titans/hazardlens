# HazardLens Risk Register

**Status:** Initial register for team review  
**Review cadence:** At kickoff and at least once per sprint  
**Scoring:** Likelihood and impact are qualitative, not measured probabilities. Re-score when new evidence is available.

| ID | Risk | Likelihood | Impact | Early warning / evidence | Mitigation and contingency | Proposed owner |
|---|---|---|---|---|---|---|
| R-01 | External MGB/PHIVOLCS services are unavailable, change schema, or have unclear coverage/query semantics. | High | High | Timeouts, changed fields, inconsistent empty responses, undocumented source date. | Verify exact layer contracts; capture sanitized fixtures; isolate per-source failures; use bounded timeouts and one retry for timeout/5xx; return `UNAVAILABLE` when semantics are unverified. Do not claim a live source works based only on mocked tests. | GIS/source + QA |
| R-02 | Empty or failed source response is misrepresented as no hazard / safe. | Medium | Critical | UI uses green/safe wording for missing data; `NO_EVIDENCE` returned on timeout. | Enforce the five-status contract; tests for empty, outside coverage, timeout, malformed payload and unsupported operations; evidence-first UI review. | Project lead + backend + QA |
| R-03 | Conflicting schema definitions or implementing all tables too early cause migration rework or data loss. | High | High | SRS table list differs from issue #1; unclear cascade/retention behavior; tables added before their workflow is needed. | Review the full 14-entity logical design, then implement physical tables incrementally with each MVP workflow; document and test types, constraints, indexes, retention and deletion behavior in each migration PR. | Database owner + project lead |
| R-04 | Geocoding violates provider terms or becomes a single point of failure. | Medium | High | Keystroke-by-keystroke requests, missing identifying User-Agent, no cache or attribution; coordinate lookup unusable when search fails. | Use explicit user-submitted search, not autocomplete against public Nominatim; retain coordinate entry/map selection as fallback. If public Nominatim is selected, use an identifying User-Agent/Referer, attribution, caching and max 1 request/second per app. Confirm provider with the team. | Backend + frontend |
| R-05 | Scope is too broad for five students and an approximately eight-week project. | High | High | AI, weather, polygon, reporting and four source integrations start before one vertical slice passes. | Prioritize one verified source-to-UI slice; defer AI/provider experiments and stretch work; review scope against sprint goal. | Project lead + whole team |
| R-06 | Team bottlenecks or unreviewed self-approval delay work / reduce quality. | Medium | High | One person owns implementation and review; many open issues have no owner; PRs stay blocked. | Confirm capacity; every active issue has one accountable assignee and a different reviewer; pair across tracks; split PRs into reviewable changes. | Whole team |
| R-07 | CI passing creates a false impression that the full application works. | High | Medium | Only lint/type/build and scaffold tests pass while source/database/UI paths remain absent. | State exactly what each CI job checks; track feature status separately; add PostGIS integration/migration checks when the database layer exists; keep smoke tests and live-source verification distinct from offline tests. | Backend + frontend + QA |
| R-08 | Session ID guessing or incorrect deletion behavior exposes one user's anonymous history to another. | Medium | Critical | API loads investigation by ID without session ownership check; cascades remove unrelated registry records. | Enforce session ownership on every read/write; test cross-session access and expiry; avoid raw IP storage; review FK cascades and retention before release. | Backend/database + reviewer |
| R-09 | Weak example credentials or leaked API keys are used outside local development. | Medium | High | `changeme` DB password or example `SECRET_KEY` used for a shared demo; secrets committed. | Treat `.env.example` values as placeholders only; generate a unique random secret per environment; keep provider keys server-side and out of commits/logs; rotate any exposed secret. | All contributors; repo admin for scanning |
| R-10 | Geospatial implementation uses the wrong SRID, geometry operation, or a false distance interpretation. | Medium | High | Point coordinates interpreted in Web Mercator; line features treated as polygons; undocumented buffer distance. | Record geometry type/SRID and exact query operation for each layer; test coordinate transforms and known points; document proximity distance semantics rather than inventing a universal hazard radius. | GIS/source + backend |
| R-11 | Unverified source metadata is presented as a publication date or resolution. | Medium | High | UI fabricates source date, resolution or coverage. | Preserve source-reported values; show “not stated in published metadata” when appropriate; keep retrieval time distinct from source publication time. | Source owner + frontend/QA |
| R-12 | AI output hallucinates, follows prompt injection, or masks source uncertainty. | Medium | High | AI creates a class, changes a status or continues when evidence is unavailable. | Keep AI deferred until core works; provide only structured evidence; use allow-listed tools, validated schemas, bounded calls, explicit AI labels and deterministic fallback; test hostile external text. | AI owner + reviewer |
| R-13 | Map tiles or geocoder failure blocks evidence retrieval. | Medium | Medium | UI cannot run coordinate-based lookup without a map tile or geocoding provider. | Keep coordinate/API investigation independent from map and geocoder; show distinct service states; use a documented fallback. | Frontend + backend |
| R-14 | Dependency versions drift or lockfiles do not match installation instructions. | Medium | Medium | CI and local install resolve different versions; Docker and direct-host setup behave differently. | Verify dependency/lockfile strategy, pin versions, use reproducible install commands and run a clean-checkout setup before release. | Backend + frontend |
| R-15 | Project board/milestones are stale or do not reflect the actual backlog. | Medium | Medium | README links exist but issue status, owners, milestone dates or dependencies are not maintained. | Verify board and milestones at kickoff; choose one source of truth for status and dates; update issue status during weekly review. | Project lead / board owner |

## Escalation rules

- Any risk that could make missing evidence look safe, leak session data, or expose secrets blocks merge/release until reviewed.
- If source semantics cannot be verified within the sprint, narrow the slice or show `UNAVAILABLE`; do not invent behavior to meet a deadline.
- If the sprint goal is at risk, defer optional features before reducing testing or review.
